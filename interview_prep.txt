PART 1: DESIGN CHOICES, ALTERNATIVES, AND REASONING
--------------------------------------------------------------------------------

1. The Agentic Workflow
-> Design Choice: Using LangGraph for the Agent (State-based routing).
-> Reasoning: Error analysis isn't always linear. Sometimes we just need to classify; sometimes we need to fetch external web docs; sometimes we can just use a cached solution to save API costs. LangGraph allows building a state machine where nodes (classify, fetch_docs, ai_analysis, cached_solution) are executed conditionally.
-> Alternatives Considered: Standard LangChain Sequential Chains or standard Python if-else statements.
-> Why not the alternative: Sequential chains are too rigid and don't allow for cyclic or conditional branching easily. Standard if-else statements become a "spaghetti" of logic once we add more complex steps (like web searching, validation, or multi-agent collaboration).

2. LLM Management
-> Design Choice: Singleton Pattern for Global LLM Manager (`GlobalLLMManager`).
-> Reasoning: The LLM client needs to be accessed by multiple components (Agent, Analyzer, AutoFixer). Re-instantiating the LLM model for every component would read config files multiple times and might cause issues if we introduce rate-limiting or local caching states in the future.
-> Alternatives Considered: Dependency Injection (passing the LLM instance to every class constructor).
-> Why not the alternative: While DI is generally good practice, for a CLI application where the configuration (provider, model, API key) is loaded globally once, a Singleton simplifies the API surface and prevents plumbing the LLM object through 5 different layers.

3. Context Window & Token Management
-> Design Choice: Targeted Codebase Ingestion (Snippets + Traceback parsing).
-> Reasoning: LLMs have token limits and charge per token. Instead of sending the whole file, the `CodebaseIngestor` parses the traceback using Regex (`r'File\s+"([^"]+)",\s+line\s+(\d+)'`), filters out `site-packages` and standard libraries, and extracts only a specific window of lines (e.g., +/- 100 lines) around the error line.
-> Alternatives Considered: Sending the entire file, or using RAG (Retrieval-Augmented Generation) across the whole project.
-> Why not the alternative: Entire files easily blow up the context window (especially for monolithic files). RAG (using a Vector DB) is overkill for a runtime error where the traceback already explicitly tells us exactly which file and line caused the crash.

4. The Auto-Fixer Mechanism
-> Design Choice: Interactive Unified Diff (`difflib`) before applying patches.
-> Reasoning: AI hallucinates. Blindly overwriting a developer's code is extremely dangerous and destroys trust. By generating a unified diff (colored in terminal) and explicitly prompting `[y/N]`, the user retains full control. Furthermore, the prompt specifically instructs the LLM to output ONLY code, preserving exact indentation and docstrings.
-> Alternatives Considered: Creating a new fixed file side-by-side, or using AST (Abstract Syntax Tree) modifications.
-> Why not the alternative: Side-by-side files pollute the workspace. AST modifications are much safer but incredibly hard to combine with LLM text generation, as LLMs output text, not AST nodes. Text-based patching with user confirmation is the sweet spot between UX and safety.

5. Application Interface
-> Design Choice: CLI Subprocess Wrapper (`TriageWrapper`).
-> Reasoning: It allows the tool to be language-agnostic. By wrapping a command (e.g., `logmaster run "python script.py"`), we capture `stdout` and `stderr` on the fly using a `deque` buffer. We intercept the stream without modifying the user's actual runtime environment.
-> Alternatives Considered: An IDE extension (VSCode) or a Python-specific decorator (`@logmaster`).
-> Why not the alternative: A decorator limits the tool to Python only. An IDE extension is much heavier to build and maintain. The CLI wrapper acts universally for Node.js, Python, Bash, etc., as long as it prints to standard output.

PART 2: POTENTIAL INTERVIEW QUESTIONS & FOLLOW-UPS
--------------------------------------------------------------------------------

Q1: "Walk me through the lifecycle of an error in your system."
* Answer strategy: 
  1. The CLI Wrapper runs the target process and buffers stdout/stderr.
  2. A regex/keyword scanner detects an error (e.g., "Traceback", "Exception").
  3. The `ErrorAnalyzer` triggers `CodebaseIngestor` to parse the traceback, dropping library files and reading only local user code snippets.
  4. The context is passed to the `Agent` (LangGraph), which classifies the error.
  5. The Agent decides whether to fetch web docs or directly query the LLM via `LLMClient`.
  6. The AI outputs a JSON/structured analysis (Cause, Fixes).
  7. If `--auto-fix` is enabled, the `AutoFixer` queries the LLM again for the exact replacement code, computes a diff, and asks for confirmation to patch the file.

Q2: "LLMs can be slow and expensive. How do you optimize for latency and cost?"
* Answer strategy: Talk about the routing logic in your LangGraph Agent. If an error is recognized as a standard/common error (via the classifier), you can return a cached solution immediately, skipping the LLM call entirely. Additionally, extracting only snippets of code (instead of whole files) drastically reduces input tokens.
* Follow-up: "What if the cached solution is outdated?" 
  -> Answer: Cache invalidation can be tied to the specific error message hash or library version. 

Q3: "How do you ensure the LLM output is parsable by your application?"
* Answer strategy: Prompt Engineering. You enforce a strict schema in the system prompt (e.g., "Format ONLY in this exact format: TYPE: ..., CAUSE: ..."). 
* Follow-up: "What if the LLM still outputs conversational text before the JSON/schema?"
  -> Answer: I use regex parsing (like in `LLMClient._parse_response`) to extract the exact lines starting with 'TYPE:', 'CAUSE:', etc. Alternatively, for a more robust V2, I would use OpenAI's Function Calling (Tools API) or Structured Outputs (JSON mode) to guarantee schema adherence.

Q4: "How does the AutoFixer ensure it doesn't break surrounding code?"
* Answer strategy: 
  1. We provide a limited context window (e.g., 200 lines) so the LLM doesn't get confused by unrelated code.
  2. The System Prompt explicitly enforces: "DO NOT remove existing comments. Preserve exact indentation."
  3. We replace ONLY the specific snippet that was sent, dynamically injecting it back into the original file content using slicing (`before + fixed_text + after`).
  4. Most importantly: The Human-in-the-loop diff confirmation.

Q5: "What happens if the underlying command (e.g. a web server) runs forever? How does your CLI wrapper handle streaming output?"
* Answer strategy: The `TriageWrapper` uses `subprocess.Popen` with `stdout=subprocess.PIPE` and iterates over `process.stdout.readline`. It prints lines in real-time to the user so it doesn't block. It uses a `deque(maxlen=100)` to keep a rolling window of the last 100 lines. When an error is detected, we already have the context in memory without eating up infinite RAM.

Q6: "How extensible is your system if we want to add a new LLM provider, like Anthropic or a local LLaMA model?"
* Answer strategy: Very extensible. Thanks to the `GlobalLLMManager` and the use of the `langchain` ecosystem, we just add a few lines of code to map a config string (e.g., "anthropic") to `ChatAnthropic`. The rest of the codebase relies on LangChain's `BaseChatModel` interface, meaning no other files need to change.

PART 3: BEHAVIORAL & "FUTURE WORK" QUESTIONS

Q7: "What was the hardest technical challenge you faced while building this?"
* Think about your actual experience. Good examples:
  - Dealing with LLM formatting hallucinations in the AutoFixer (when it randomly wraps code in markdown ```python fences).
  - Figuring out how to parse tracebacks reliably across different OS/languages.
  - Making the real-time CLI wrapper work smoothly without messing up terminal encodings or dropping lines.

Q8: "If you had 3 more months to work on this, what would you add?"
* Great ideas to mention:
  1. Multi-language Support: Extending the `CodebaseIngestor` to understand Node.js, Go, and Rust tracebacks natively.
  2. RAG for Entire Repos: Integrating a local vector database (like Chroma or FAISS) to index the whole repository, allowing the AI to fix errors that require context from multiple distant files (e.g., an interface changed in `A.py` which broke `B.py`).
  3. Local Models integration: Full support for Ollama so enterprise code never leaves the machine.
  4. Agentic Web Search: Allowing the LangGraph agent to dynamically search StackOverflow or GitHub issues when it encounters a completely unknown error.

PART 4: MEDIUM-LEVEL / ML-SPECIFIC QUESTIONS
--------------------------------------------------------------------------------

Q9: "At what point would you consider fine-tuning an open-source model (like Llama 3) for this specific task instead of using zero-shot prompting?"
* Answer strategy: 
  - Fine-tuning becomes necessary when zero-shot/few-shot prompting fails to capture domain-specific patterns, or when you need to optimize for latency/cost by using a smaller model (e.g., 8B parameters) that performs on par with a larger one (like GPT-4).
  - The dataset would consist of (Code Snippet + Traceback) as input, and (Structured JSON Analysis + Corrected Code) as output.
  - Mention PEFT (Parameter-Efficient Fine-Tuning) techniques like LoRA/QLoRA to do this efficiently without massive GPU clusters.

Q10: "If an error stack trace involves 5 different files and exceeds the model's context window, how could you use ML to extract the most relevant functions?"
* Answer strategy: 
  - Introduce Retrieval-Augmented Generation (RAG).
  - You would chunk the entire codebase (e.g., at the function or class level).
  - Use an embedding model (like text-embedding-3-small or all-MiniLM) to convert chunks into vector representations and store them in a Vector DB (like ChromaDB or FAISS).
  - When an error occurs, embed the traceback and perform a cosine similarity search against the Vector DB to retrieve the Top-K most semantically relevant functions to include in the context, staying within token limits.

Q11: "How do you evaluate the accuracy of your error classifier and the proposed code fixes?"
* Answer strategy: 
  - For the classifier (which outputs error types), use standard classification metrics like Precision, Recall, and F1-score on a golden dataset of known errors.
  - For the code fixes (Generative output), standard NLP metrics like BLEU or ROUGE are poor indicators for code. Instead, use functional evaluation (Execution-based evaluation).
  - You would run a sandbox environment (like Docker), apply the AI's fix, run the test suite, and check if the tests pass (pass@k metric). Also, you can use "LLM-as-a-judge" to have a stronger model evaluate the fix's quality and safety.

Q12: "In your LangGraph implementation, how do you handle state machine failures, such as infinite loops if the LLM fails to provide a parseable response?"
* Answer strategy:
  - Add state variables like `retry_count` to the `AgentState`.
  - In conditional edges, check if `retry_count > MAX_RETRIES`. If it exceeds the limit, route to a fallback `END` node that returns a generic "Analysis failed" message.
  - You can also implement a temperature fallback strategy (e.g., retry with temperature=0.0 for more deterministic parsing if the first attempt fails).

Q13: "LLMs often hallucinate nonexistent APIs or libraries. How could you programmatically verify a hallucinated fix before presenting it to the user?"
* Answer strategy:
  - Static Analysis: Before showing the diff, run a tool like `flake8` or `mypy` on the patched file. If the static analyzer throws a "ModuleNotFoundError" or "AttributeError", the fix is likely hallucinated.
  - Agentic feedback loop: Feed the static analysis error back into the LLM as a new state in LangGraph, asking it to correct its hallucination (Self-Correction workflow).
